# SQL 初始化脚本维护

## 核心规则

- 将每个应用依赖的初始化 SQL 放在该应用对应工程的 `./init/db/` 目录下。
- 先确定实际运行该 SQL 的应用归属，再选择目录；不要因为发布使用 Helm/Charts 就把应用 SQL 复制到 `b2b-charts`。只有 Charts 自身拥有该初始化职责时，才修改 Charts。
- 每个新增或维护的 SQL 脚本，必须在文件开头增加 `use <数据库名>;`，并将其作为第一条可执行语句（前面只允许保留注释或空行），明确脚本执行的目标数据库；数据库名必须与应用 datasource 配置一致。
- 每个新增脚本使用纯数字递增文件名，例如 `001.sql`、`002.sql`、`003.sql`。沿用目标目录已有的补零位数和命名风格。
- 已执行过的编号永远不可复用，也不要修改已执行脚本来承载新变更；所有新变更都创建新的编号脚本。
- 编号不能只看当前工作区文件：同时检查 Git 历史、部署清单和初始化执行记录；若无法确认已执行的最大编号，先停止并说明缺口。

## 新增脚本流程

1. 定位应用工程及其 `init/db/` 目录；确认 SQL 使用的数据库与该应用运行时连接一致，并确定脚本开头 `use <数据库名>;` 中的数据库名。
2. 列出目录内已有脚本，并查询历史中曾使用过的编号。取“现存或历史最大编号 + 1”，不要填补中间空号。
3. 检查是否已有相同 DDL、相同表或相同业务变更，避免重复初始化。
4. 使用 `apply_patch` 创建新的编号脚本。先写入文件头 `use <数据库名>;`，确保它是第一条可执行语句；保持现有脚本的 SQL 方言、字符集、注释、`USE` 语句和幂等风格；不要顺手重排旧脚本。
5. 如果一次需求需要多个脚本，为每个脚本预留不同的连续编号，并按依赖顺序命名；不要让多个脚本共用编号。
6. 对 Git 子模块，在子模块目录内检查新增文件状态；向用户说明父仓库只会看到子模块指针变脏，脚本归属于子模块自己的变更。

## 编号与执行安全

- 初始化系统通常按文件名顺序执行且记录已执行编号，因此编号是不可变的发布身份，不是临时文件名。
- 不要删除、重命名或覆盖已执行脚本；即使脚本内容有误，也新增修复脚本。
- 不要为了“看起来完整”把 `002.sql` 改回 `001.sql`，也不要复用历史上已经执行但当前目录缺失的编号。
- 是否使用 `CREATE TABLE IF NOT EXISTS`、`ALTER TABLE` 前置判断或其他幂等写法，遵循该应用现有初始化约定；不能用幂等写法掩盖错误的编号或错误的应用归属。
- 不要直接连接线上执行 SQL；本技能只维护脚本文件，线上执行由既有发布/初始化流程负责。

## 完成前检查

- 确认脚本路径是目标应用的 `init/db/<新编号>.sql`。
- 确认新编号大于该目录现有编号和已执行历史编号，且没有重复。
- 确认脚本开头第一条可执行语句为 `use <数据库名>;`，且数据库名、表名和应用 datasource 配置一致。
- 用 `rg` 搜索表名和脚本编号，确认没有重复脚本或误放到其他应用目录。
- 执行 `git diff --check`；对新文件使用 `git status` 和直接查看内容确认变更已被 Git 识别。
- 如果仓库提供 SQL lint、迁移校验或初始化 dry-run，执行相应检查；没有工具时至少做静态语法和依赖顺序检查，并在交付中说明未连接数据库验证。

## 交付说明

说明新增脚本的完整路径、编号、所属应用、涉及数据库/表，以及验证结果。若发现线上缺表、初始化记录缺失或 Charts 未包含脚本，明确标记为发布/运维待办，不私自修改无关工程。
